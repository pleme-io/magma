# Lava Integration — caixa + tatara-lisp as magma-native concepts

> **Status**: design. Lava suite repos live (lava-core, lava-arch, lava-architectures, lava-contracts, lava-stack, lava-forge, lava-aws, lava-cloudflare, lava-kubernetes, lava-helm, lava-akeyless, lava-api-forge). This doc defines how they slot into magma so operators author infrastructure entirely in tatara-lisp + caixa, with magma owning plan/apply/state.

## Vision

```
operator writes:                       ┌─────────────────────────────┐
                                       │ architecture.tlisp          │
                                       │  (deflava-architecture       │
                                       │     aws-vpc-network          │
                                       │     :resources ...))         │
                                       └──────────────┬──────────────┘
                                                      │
                                       ┌──────────────▼──────────────┐
                                       │ magma plan architecture.tlisp│
                                       │   ↓ (in-memory eval)         │
                                       │ lava_architectures::eval     │
                                       │   ↓                          │
                                       │ lava_core::Architecture      │
                                       │   ↓ render_terraform_json     │
                                       │ serde_json::Value            │
                                       │   ↓ magma_plan::Plan          │
                                       │   ↓ magma_apply::Scheduler    │
                                       │   ↓ tfplugin5/6 gRPC         │
                                       │ provider (lava-aws-provider) │
                                       │   ↓ AWS API                  │
                                       │ cloud state                  │
                                       └──────────────────────────────┘
```

Magma understands three first-class inputs:

| Input | Loaded via | Use case |
|---|---|---|
| `architecture.tlisp` | `lava_architectures::eval_architecture` | Declarative composition |
| `caixa.lisp` (`:kind :Aplicacao`) | `lava_caixa::load_aplicacao` | Whole-app deployment bundles |
| `terraform.json` | direct | Legacy / pangea-rendered output |

All three converge on `lava_core::Architecture` → `magma_types::Plan`. Same downstream pipeline.

## Required magma changes

### 1. New crate: `magma-lava`

Wraps the existing `lava-*` crates into one façade magma consumes:

```rust
// magma-lava/Cargo.toml
[dependencies]
lava-core         = { ... }
lava-arch         = { ... }
lava-architectures = { ... }
lava-contracts    = { ... }
lava-stack        = { ... }
magma-types       = { path = "../magma-types" }

// magma-lava/src/lib.rs
pub fn load_architecture_tlisp(
    src: &str,
    bindings: &lava_architectures::InputBindings,
) -> Result<magma_types::Plan, LavaError> {
    let arch = lava_architectures::eval_architecture(src, bindings)?;
    let tf_json = arch.render_terraform_json()?;
    let plan = magma_config::config_from_terraform_json(&tf_json)?;
    Ok(plan)
}

pub fn load_caixa_aplicacao(
    caixa_src: &str,
) -> Result<magma_types::Plan, LavaError> {
    let caixa = lava_caixa::parse(caixa_src)?;
    let archs = caixa.member_architectures()?;  // resolves :membros slot
    let merged = lava_arch::merge_all(&archs);
    let tf_json = merged.render_terraform_json()?;
    let plan = magma_config::config_from_terraform_json(&tf_json)?;
    Ok(plan)
}
```

### 2. Magma CLI extensions

`magma-cli` adds two new subcommand flavors (no breaking changes — `.tf.json` input still works):

```sh
# Plan/apply a tatara-lisp architecture file directly.
magma plan  --tlisp architecture.tlisp [-- --name=prod --cidr=10.1.0.0/16]
magma apply --tlisp architecture.tlisp --auto-approve

# Plan/apply a caixa.lisp Aplicacao bundle (multi-service stack).
magma plan  --caixa caixa.lisp [-- --env=prod]
magma apply --caixa caixa.lisp --auto-approve

# Existing terraform.json path unchanged.
magma plan  --config terraform.tf.json
```

Behind the scenes both routes flow through `magma-lava::load_*` → typed `magma_types::Plan`.

### 3. Stack-aware backend selection

`lava_stack::Stack` already carries `BackendRef` (Local/S3/GCS/AzureBlob). Magma reads it directly:

```sh
magma plan --stack prod-us-east-2.tlisp
# parses deflava-stack form
# extracts backend + workspace + variable overrides
# uses backend for state read/write (replaces magma-backend's
#   command-line backend-config flags)
```

### 4. Provider plugin path resolution

`lava-aws-provider` (autogenerated by `lava-provider-gen` from `lava-api-forge` output) ships as a standard tfplugin5/6 binary at `${HOME}/.local/share/magma/plugins/registry.lava.pleme-io/aws/<version>/<os_arch>/lava-aws-provider`.

Magma's existing `magma-providers` crate discovers it the same way it discovers any tfplugin provider — no special-case path.

## Pipeline correctness contract

| Stage | Invariant |
|---|---|
| **Author** | `.tlisp` source is pure data — no I/O, no side effects |
| **Eval** | `eval_architecture(src, bindings)` is deterministic — same inputs → byte-equal `Architecture` |
| **Render** | `Architecture::render_terraform_json()` is byte-deterministic — IndexMap preserves insertion order |
| **Plan** | `config_from_terraform_json` produces same `Plan` as pangea+tofu would produce |
| **State** | post-apply `terraform.tfstate` is byte-equivalent to pangea+tofu run (modulo recorded timestamps) |

This contract is the foundation of the "repeatable infrastructure" guarantee. Same `.tlisp` source, anywhere → same state, anywhere.

## Validation harness (lava-equivalence)

A new repo `lava-equivalence` runs an end-to-end diff against every architecture in `lava-architectures/`:

1. For each `<name>.tlisp`:
   - Evaluate via `lava_architectures::eval_architecture`
   - Render to terraform.json (A)
   - Run pangea's `Pangea::Architectures::<Name>.build` (B)
   - Diff A vs B with sorted keys
2. Report per-architecture: byte-equivalent | drift detected
3. CI gate: any drift fails the build

This is the "even state matches when we run" proof the operator asked for. The byte-equivalence test already landed for `aws-vpc-network` (see `lava-architectures/src/lib.rs::aws_vpc_network_tlisp_renders_byte_equivalent_to_pangea_spec`).

## How "caixa-native" cashes out

Today: a caixa-* repo is a typed package + lifecycle (caixa-core directive). Caixas with `:kind :Aplicacao` declare a service mesh via `:membros` + `:contratos` + `:placement`. **Magma reads these directly**:

```lisp
(defcaixa my-product
  :kind :Aplicacao
  :membros (
    (lava-aws-vpc-network :inputs (:cidr "10.0.0.0/16"))
    (lava-akeyless-aws-integration :consumes (network))
    (lava-eks-cluster :consumes (network secrets) :inputs (:node-count 3))
    (lava-prometheus-stack :placement (:cluster-ref cluster)))
  :workspace "prod"
  :backend (:s3 :bucket "pleme-tf-state" :key "prod/my-product.tfstate"))
```

`magma apply --caixa caixa.lisp` does:
1. Parse caixa.lisp → `lava_caixa::Aplicacao`
2. Resolve each `:membros` ref to its `.tlisp` source (from lava-architectures or external repo)
3. Compose into one `lava_core::Architecture` honoring `:consumes` deps
4. Render → `magma_types::Plan` → apply via tfplugin providers

One operator command. Multiple typed primitives layered. Pure tatara-lisp authoring throughout.
